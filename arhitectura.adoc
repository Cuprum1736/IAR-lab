== 7. Программная архитектура

Разработка программного обеспечения метеостанции базируется на трехуровневой архитектуре: аппаратный уровень (Hardware Abstraction Layer, HAL), уровень драйверов и уровень приложения (FreeRTOS задачи). Такой подход обеспечивает модульность, переносимость кода и удобство отладки.

Верхний уровень (Application Layer) отвечает за логику сбора и передачи данных.
Средний уровень (Middleware) предоставляет сервисы реального времени и очереди сообщений.
Нижний уровень (Hardware Layer) обеспечивает абстракцию от конкретного микроконтроллера и периферии.

Взаимодействие между уровнями строго регламентировано: задачи приложения не обращаются к регистрам напрямую, а используют API драйверов.

=== 7.3. Словесное описание работы программы

Программа начинает своё выполнение с функции `main()`, в которой происходит инициализация всей системы. На первом этапе настраивается тактирование микроконтроллера: внешний кварц на 8 МГц через PLL умножается до рабочей частоты 100 МГц. Затем инициализируется периферия: выводы GPIO для I2C1 (пины PB6 и PB7 для подключения BME280) и для USART2 (пины PA2 и PA3 для подключения Bluetooth-модуля HC-06).

После настройки периферии программа переходит к инициализации драйверов. Драйвер BME280 выполняет сброс датчика, чтение калибровочных коэффициентов из NVM (энергонезависимой памяти датчика) и настройку режима работы: oversampling ×1 для всех каналов, нормальный режим с периодом 100 мс. Драйвер HC-06 настраивает USART2 на скорость 9600 бод и отправляет тестовую AT-команду для проверки работоспособности модуля.

Затем создаётся очередь FreeRTOS `WeatherQueue` размером на 5 элементов. Эта очередь будет использоваться для передачи данных от задачи-измерителя к задаче-отправителю.

Далее создаются две задачи FreeRTOS. Первая задача — `SensorTask` — получает более высокий приоритет (2), вторая — `BluetoothTask` — более низкий приоритет (1). После создания задач вызывается `vTaskStartScheduler()`, после чего управление переходит к планировщику FreeRTOS, и задачи начинают выполняться согласно своим приоритетам и периодам.

**Работа задачи SensorTask:**

Задача `SensorTask` выполняется строго каждые 100 миллисекунд с использованием механизма `vTaskDelayUntil`, который обеспечивает точный период без накопления ошибки.

На каждом цикле выполнения задача выполняет следующие действия:
1. Через драйвер BME280 выполняет чтение регистров данных датчика по I2C. Чтение происходит пакетно: за один сеанс связи читаются все 8 байт (3 байта давления, 3 байта температуры, 2 байта влажности). Это гарантирует согласованность данных.
2. Полученные сырые значения АЦП (adc_P, adc_T, adc_H) передаются в математические функции компенсации.
3. Вычисляется температура: сначала через промежуточные переменные var1 и var2 рассчитывается значение t_fine, которое затем преобразуется в температуру с разрешением 0.01°C. t_fine сохраняется в глобальной переменной для использования в формулах давления и влажности.
4. Вычисляется давление с использованием 64-битной арифметики. Формула использует t_fine и девять калибровочных коэффициентов. Результат возвращается в формате Q24.8 (давление в Паскалях × 256).
5. Вычисляется влажность с использованием t_fine и шести калибровочных коэффициентов. Результат возвращается в формате Q22.10 (влажность в % × 1024). Выходное значение ограничивается диапазоном от 0 до 100% RH (клиппинг).
6. На основе полученных температуры и влажности по формуле Магнуса вычисляется точка росы:

   α = (17.27 × T) / (237.7 + T) + ln(RH / 100)
   
   Td = (237.7 × α) / (17.27 - α)

7. Все четыре величины (температура в °C, давление в гПа, влажность в %, точка росы в °C) упаковываются в структуру `WeatherData`. Также в структуру записывается временная метка `timestamp` (значение системного таймера в миллисекундах) и флаг `valid = true`.
8. Структура отправляется в очередь `WeatherQueue` с нулевым временем ожидания (операция неблокирующая). Если очередь заполнена, данные не отправляются, но флаг переполнения инкрементируется в счётчике.
9. Задача переходит в состояние ожидания на 100 миллисекунд до следующего цикла.

**Обработка переполнения очереди:**

Поскольку задача `SensorTask` отправляет данные каждые 100 мс, а задача `BluetoothTask` извлекает их каждые 1000 мс, за 1 секунду в очередь поступает 10 сообщений, а извлекается только 1. Размер очереди установлен в 5 элементов, что приводит к её регулярному переполнению.

На каждый случай переполнения счётчик `overflowCounter` увеличивается. Однако это не является критической проблемой для метеостанции, так как:
- Погодные параметры изменяются относительно медленно
- Потеря нескольких промежуточных измерений не влияет на конечный результат
- Наиболее свежие данные всегда имеют приоритет (очередь не блокирует отправку)

При переполнении новые данные просто не попадают в очередь, а задача `SensorTask` продолжает свою работу без задержек. Пользователь может отследить количество переполнений через диагностическую команду (при реализации).

**Работа задачи BluetoothTask:**

Задача `BluetoothTask` выполняется каждые 1000 миллисекунд.

На каждом цикле выполнения задача выполняет следующие действия:
1. Пытается получить данные из очереди `WeatherQueue` с таймаутом 100 миллисекунд.
2. **Если данные успешно получены:** задача сохраняет их в глобальную структуру `lastValidData` и обнуляет счётчик потерь `lossCounter`.
3. **Если данные не получены (таймаут):** задача инкрементирует счётчик `lossCounter` и продолжает использовать последние валидные данные из `lastValidData`.
4. Формируется выходная строка по заданному в техническом задании формату с использованием модуля `StringFormatter`. Формат строки:

   `"Давление: XXX.XX гПа Влажность: XXX.XX % Температура: XXX.XX C Точка росы: XXX.XX C\r\n"`

   Форматирование выполняется с помощью функции `snprintf`, которая гарантирует безопасную работу с буфером и предотвращает переполнение строки.
5. Строка отправляется через драйвер HC-06 по USART2. Если передача не удалась (например, модуль отключён), драйвер выполняет до 3 повторных попыток.
6. Задача переходит в состояние ожидания на 1000 миллисекунд до следующего цикла.

**Механизм сохранения последних валидных данных:**

Важной особенностью архитектуры является то, что задача `BluetoothTask` всегда имеет данные для отправки, даже если очередь пуста или датчик временно недоступен. Это достигается за счёт хранения последних успешно полученных данных в статической структуре `lastValidData`. При запуске системы эта структура инициализируется значениями по умолчанию (температура 0°C, давление 1013.25 гПа, влажность 50%, точка росы вычисляется по формуле). После первого успешного измерения структура обновляется и сохраняет актуальные значения до следующего обновления.

Этот механизм гарантирует, что на смартфон или ПК всегда поступают осмысленные данные, даже при временных сбоях связи с датчиком BME280. Пользователь может отследить качество данных по счётчику `lossCounter` — если он постоянно растёт, это указывает на проблемы с датчиком или переполнение очереди.

**Взаимодействие задач и обработка ошибок:**

Обе задачи работают независимо под управлением планировщика FreeRTOS. Поскольку `SensorTask` имеет более высокий приоритет (2), чем `BluetoothTask` (1), планировщик всегда будет отдавать предпочтение сбору данных, а не их отправке. Это гарантирует, что период измерения 100 мс будет соблюдаться даже при высокой загрузке USART2 или при зависании Bluetooth-модуля.

При возникновении ошибок I2C при обмене с BME280 драйвер выполняет автоматическое восстановление: сбрасывает шину, повторяет передачу до 3 раз. Если все попытки неудачны, драйвер возвращает код ошибки, и задача `SensorTask` пропускает текущий цикл измерения, используя предыдущие данные (через флаг `valid=false` в структуре). Счётчик ошибок I2C инкрементируется для диагностики.

При ошибках USART2 (например, Bluetooth-модуль отключён) драйвер HC-06 также выполняет повторные попытки, но задача `BluetoothTask` продолжает отправлять данные — они просто теряются, но программа не блокируется. Восстановление связи происходит автоматически при повторном подключении модуля.

**Диагностика и мониторинг:**

Программа ведёт внутреннюю статистику, которая может быть полезна при отладке и эксплуатации:

| Счётчик | Назначение |
|---------|-------------|
| `overflowCounter` | Количество переполнений очереди (сколько измерений было потеряно) |
| `lossCounter` в BluetoothTask | Количество циклов, когда очередь была пуста |
| `i2cErrorCounter` | Количество ошибок I2C при обмене с BME280 |
| `uartErrorCounter` | Количество ошибок USART2 при отправке на HC-06 |

Эти счётчики могут быть выведены по специальной команде (например, при нажатии кнопки или отправке символа через Bluetooth), что позволяет оценить качество работы системы.

=== 7.8. Вывод по программной архитектуре

Разработанная программная архитектура полностью удовлетворяет требованиям технического задания:

1. Используется **FreeRTOS** для управления задачами реального времени
2. Задачи имеют чётко определённые периоды: 100 мс для опроса датчика и 1000 мс для отправки по Bluetooth
3. Взаимодействие между задачами организовано через **очередь сообщений** с защитой от переполнения
4. Предусмотрен **механизм сохранения последних валидных данных**, гарантирующий, что на выход всегда подаются осмысленные значения
5. Драйверы BME280 и HC-06 инкапсулируют работу с периферией через **HAL**
6. Обработка ошибок включает повторные попытки при сбоях I2C и USART, а также подсчёт статистики для диагностики

Ключевой особенностью архитектуры является сознательно допущенное переполнение очереди (размер 5 элементов при скорости поступления 10 сообщений в секунду). Это не является проблемой для метеорологического приложения, где важны только актуальные данные, а не все промежуточные измерения. При этом механизм последних валидных данных гарантирует, что на Bluetooth всегда передаются осмысленные значения.

Данная архитектура является основой для последующей реализации кода в среде разработки.
