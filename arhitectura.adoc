== 7. Программная архитектура

Разработка программного обеспечения метеостанции базируется на трехуровневой архитектуре: аппаратный уровень (Hardware Abstraction Layer, HAL), уровень драйверов и уровень приложения (FreeRTOS задачи). Такой подход обеспечивает модульность, переносимость кода и удобство отладки.

Верхний уровень (Application Layer) отвечает за логику сбора и передачи данных.
Средний уровень (Middleware) предоставляет сервисы реального времени и очереди сообщений.
Нижний уровень (Hardware Layer) обеспечивает абстракцию от конкретного микроконтроллера и периферии.

Взаимодействие между уровнями строго регламентировано: задачи приложения не обращаются к регистрам напрямую, а используют API драйверов.

=== 7.9. Обработка ошибок

В программной архитектуре предусмотрены следующие механизмы обработки ошибок:

1. **Watchdog (IWDG):** Независимый сторожевой таймер с периодом срабатывания 4 секунды. Перезапускается в `CSensorTask` при успешном проходе цикла. При зависании ПО выполняет аппаратный сброс.

2. **Обработка ошибок I2C:**
   - При возникновении ошибки (NACK, потеря арбитража) драйвер выполняет сброс шины
   - Выполняется до 3 попыток перечтения данных перед возвратом ошибки

3. **Обработка ошибок очереди:**
   - Если очередь переполнена, старые данные не перезаписываются
   - `CBluetoothTask` при отсутствии новых данных использует последние валидные (`m_lastData`)

4. **Обработка ошибок USART:**
   - При ошибке передачи выполняется повторная отправка (до 3 раз)
   - При ошибке инициализации HC-06 задача продолжает работу, используя последние валидные данные

=== 7.11. Особенности реализации C++ обёртки

В соответствии с требованием ТЗ, используется C++ обёртка над FreeRTOS. Ключевые особенности:

1. **Статическая функция-обёртка:** Класс `CTask` содержит статический метод `taskFunction(void* pvParameters)`, который получает указатель `this` и вызывает виртуальный метод `run()`.

2. **Использование `new` и `delete`:** Задачи и очереди создаются динамически через `new`, что позволяет гибко управлять памятью.

3. **Типобезопасная очередь:** Класс `CQueue` использует шаблоны или принимает размер элемента в конструкторе, что позволяет передавать структуры без приведения типов.

4. **Поддержка исключений:** Код не использует исключения C++ для сохранения детерминизма RTOS. Ошибки обрабатываются через возвращаемые коды (`bool`, `ErrorStatus`).

=== 7.12. Взаимодействие с аппаратными регистрами через HAL

Программная архитектура строго соблюдает разделение уровней:

| Уровень | Доступ к регистрам | Пример |
|---------|-------------------|---------|
| Прикладной | Запрещён | Нет прямых обращений к `GPIOB->ODR` |
| Драйверы | Через HAL | `HAL_I2C_Master_Transmit()`, `HAL_UART_Transmit()` |
| HAL (STM32) | Прямой (инкапсулирован) | `I2C1->CR1`, `USART2->BRR` |

Такая иерархия обеспечивает:
- Переносимость кода между проектами
- Возможность модульного тестирования
- Упрощение отладки

=== 7.13. Вывод по программной архитектуре

Разработанная программная архитектура полностью удовлетворяет требованиям технического задания:

1. Используется **FreeRTOS** с **C++ обёрткой** (классы `CTask`, `CQueue`, `CSemaphore`)
2. Применяется **многоуровневая архитектура** с чёткими границами ответственности
3. Архитектура документирована с использованием **UML** (диаграммы классов, последовательности, активности)
4. Взаимодействие между задачами организовано через **типобезопасную очередь**
5. Драйверы `BME280Driver` и `HC06Driver` инкапсулируют работу с периферией через **HAL**
6. Предусмотрены механизмы **обработки ошибок** (Watchdog, повторные попытки, использование последних валидных данных)

Данная архитектура является основой для последующей реализации кода в среде разработки.
